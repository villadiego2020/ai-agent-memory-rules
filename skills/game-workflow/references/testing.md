# Explainable game verification

Select checks by a named requirement or risk, severity, likelihood and the cheapest layer that can prove it. Do not add tests that merely copy implementation. Existing focused checks can be sufficient for a localized reversible edit.

For each check record requirement/risk, why it matters, setup/action, expected observable, actual evidence/result and limits (what a pass does and does not prove). Use a compact list or, for several parallel cases:

| Risk/requirement | Why | Setup/action | Expected observable | Actual evidence/result | Limits |
| --- | --- | --- | --- | --- | --- |

Mark unexecuted checks NOT RUN; after execution use PASS, FAIL or BLOCKED with actual assertions/logs/screenshots/video/profiler evidence. Separate a product failure from missing environment/tooling. Include version/build/topology/seed when needed for reproduction.

## Test handoff for every delivered work item

The orchestrator always lists both EditMode and PlayMode tests after each task or independently delivered work item, including small edits. Inventory tests relevant to changed behavior and adjacent risks, not the whole repository unless explicitly requested. Inspect the relevant test files/assemblies before naming runnable tests; use exact names and paths or suite/filter names. For each entry explain its purpose, expected observable and current status/evidence. Clearly label proposed missing coverage as not yet implemented. If a mode has no applicable tests, state why; non-Unity work still reports both modes as not applicable.

Before executing pending Unity tests, the orchestrator presents this inventory and asks in the user's language whether AI should run them or the user will run them in Unity Test Runner. Wait for the choice unless that scope was already authorized. Previously run tests retain their actual results; do not automatically rerun them or ask for the same authorization again. When there are no runnable tests, explain the gap without offering an unavailable run. Subagents supply the inventory/results to the orchestrator and follow its authorized scope; they do not ask separately or start Unity tests before the choice.

For manual execution, give the EditMode/PlayMode tab, test assembly/suite/filter, required scene/setup and expected outcome. Await the user's actual results; do not infer a pass from their choice to run manually. While required evidence is pending, report "Implementation complete; verification pending" and leave required QA/work open. Independent inspection, compilation and other authorized checks may proceed. Follow applicable Unity session ownership rules; a test-run choice does not authorize shared Main Editor Play Mode.

## Focused UTF selection and execution

This is an agent execution contract across projects, not a guarantee that every connector enforces it. Inspect the installed connector's capabilities and semantics; report a missing preflight or state capability rather than pretending it exists. Preserve explicit user overrides, including an intentionally authorized full-mode run; never broaden scope implicitly.

1. Pin the project/Editor identity and inspect the relevant source tests, assembly definitions and mode. After compilation settles, discover the relevant tests once per compiled/source state; reuse that discovery until a relevant source, assembly, compilation or target change invalidates it. Prefer discovered fully qualified fixture/test names plus assembly names, or the equivalent fixture/test and assembly selection in Unity Test Runner. Keep source-inspected candidates distinct from compiled, discovered tests. Regex is an explicit selection option, never an inferred default.
2. Before starting, resolve the selection against that discovery and record its mode, exact names/assemblies and nonzero count. Confirm they match the authorized inventory. Reject unresolved names, zero matches and accidental selection of every test in a mode. Never retry with an empty filter or silently broaden to the whole assembly/mode. For regex, preflight its actual resolved names/count too. If the installed interface cannot resolve a selection safely, report BLOCKED and offer the equivalent manual GUI selection; do not run an uncertain scope.
3. Serialize discovery/run operations per Editor. Check for an existing active run before submission and retain the pinned Editor and selection throughout the operation. While active, do not switch targets, change filters/source or trigger compilation, refresh or another run. Do not use raw execute-code to bypass a running-test guard. A cooperating agent uses the same assigned operation serially; an unrelated run remains user-owned.
4. Keep lifecycle evidence separate: request accepted is not discovery completed; discovery is not start; start is not proof of running; running is not terminal success. Retain the operation identifier when supported and require terminal results with the selected tests and actual outcomes. Check expected versus executed counts and explain skipped, missing or extra tests; a tool acknowledgement, missing results or zero executed tests is not PASS.
5. Before submission, choose overall and no-progress time budgets, expected progress signals and a polling interval/attempt cap appropriate to the selected count, mode, fixture setup and known durations. Track discovery, start and running progress separately; refresh the no-progress clock only on meaningful phase/test/result changes. Poll with bounded waits and retain opportunities to communicate. On a budget expiry or lost response, inspect operation state, compilation, logs and Editor responsiveness; report the last confirmed phase and remaining uncertainty. Do not automatically restart or resubmit: first establish whether the original run is active or terminal. Preserve the user's Editor; use supported cancellation only within existing authority and ownership, never kill/relaunch it as a timeout workaround.
6. For a speed comparison, benchmark the exact same resolved selection, mode, Editor/build and equivalent warm compilation/discovery/cache state. Record discovery/start/execution/total time separately where observable. A smaller selection, cold-versus-warm difference or acknowledgement latency does not establish faster test execution. These prose requirements alone are not a measured performance improvement.

UTF automated EditMode/PlayMode tests use the authorized test runner and are distinct from managed gameplay Player sessions. Do not build/start a managed gameplay Player solely to run UTF tests unless that is the project's explicit test setup. A gameplay/playtest request still follows owned managed Player routing. Any actual shared Main Editor Play Mode transition, including a connector's UTF PlayMode path, requires explicit user intent naming that target. The test-run choice may already include that explicit Main Test Runner target; retain its authorization without asking again. A generic choice to run tests does not authorize shared Main Editor Play Mode, and labeling an operation as a test does not bypass session ownership.

## Behavioral coverage

Select applicable game scenarios: state transitions and invalid actions; scene reload, pause, rematch, pooling and subscription cleanup; config defaults and migration/save compatibility; input navigation and rendered UI; hot-path/frame allocations.

For networking select cases from the actual contract: unauthorized or malformed client intent, host versus dedicated/headless, late join, reconnect, duplicates/reorder/loss/jitter, prediction/reconciliation/resimulation, interest boundaries, version mismatch, and bandwidth/memory thresholds at stated load. Do not assume one framework's behavior in another version.

Compilation proves compile compatibility, not gameplay or visual behavior. Report expected/actual, severity, evidence and source location for a failure; label suspected root causes as inference. State reduced risks and remaining coverage limits. A tester may edit only explicitly assigned test files, never production code or Memory.
